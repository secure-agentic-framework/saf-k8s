# SAF-K8S-1001-030 — Centralized AI workload log collection and routing

Run from the SAF-K8S framework checkout.

```sh
python3 tests/control-lab/lab.py test SAF-K8S-1001-030 --docker-context desktop-linux
```

The runner creates its own kind v1.36.1 cluster, default `saf-test` namespace,
evidence directory, and cleanup lifecycle. This case does not invoke Beads.

## Case behavior

Three harmless workload fixtures write one fixed JSON record to container stdout:

| Workload type | Kubernetes object | Stable event ID |
| --- | --- | --- |
| Training | completed `batch/v1` Job | `saf-1001-030-training-event-001` |
| Inference | request to a fixture HTTP endpoint through an internal Service | `saf-1001-030-inference-event-001` |
| Pipeline | completed staged `batch/v1` Job | `saf-1001-030-pipeline-event-001` |

The collector uses the Kubernetes API `pods/log` subresource. Its namespaced Role
allows only `get` on `pods/log` for the three exact fixture Pod names. The collector
does not list Pods or read other Pod logs. Workload containers do not receive a
service-account token. The receiving router has token automount disabled and accepts
only case-owned fixture records.

The red probe collects all three source records while the router's route is absent;
each POST receives the exact route-missing response and the receiver remains empty.
The case then approves the case-owned `fixture-pod-logs` route, re-reads the same
source log lines, and checks that the receiver gets each event once with the exact
namespace, Pod, container, workload type, event ID, event type, and message. A
separate host-side `kubectl logs` read compares the actual stdout lines directly to
`fixtures.json`.

Stable results are recorded through `lab.check`. The raw API Pod objects, collected
stdout, approval response, source logs, and receiver state are retained as separate
files in the runner's evidence directory. Job Pod names, object UIDs, and timestamps
are generated by Kubernetes and are evidence values; they are not hard-coded as test
expectations.

## Scope limits

This is a local collection and routing fixture. It does not deploy Fluent Bit or a
production collector, connect to an enterprise logging platform, prove tenant
segregation, retention, tamper protection, completeness over time, alerting, or
recovery after an outage. Kubernetes documents container stdout/stderr capture,
API access, and separate cluster-level logging architectures. The workload names
and event schemas are specific to these fixtures. The inference request produces
one stdout event. The collector reads all three events through Kubernetes
`pods/log` and forwards them independently.
