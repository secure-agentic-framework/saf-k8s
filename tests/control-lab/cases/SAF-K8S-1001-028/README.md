# SAF-K8S-1001-028 — AI-specific SIEM source onboarding and forwarding

## Invocation

Run from the SAF-K8S framework checkout.

```sh
python3 tests/control-lab/lab.py test SAF-K8S-1001-028 --docker-context desktop-linux
```

The case uses a separate audit-configured Kind v1.36.1 cluster and deletes it
when the test finishes.

## What it proves

The case creates a named audit marker ConfigMap through the Kubernetes API.
It matches the response `Audit-Id` to the corresponding `ResponseComplete`
record in the case-owned audit file. The event sent through the local connector
preserves that `auditID` and the origin `kube-apiserver/audit-policy-file`.

Five in-cluster one-shot fixture Pods submit fixed, synthetic event records. Before their routes are enabled, the connector returns HTTP 404 and the owned receiver contains none of those AI event types. After enabling the routes, the same five `event_id` values and event types are resubmitted and appear once at the receiver with their expected `source_origin`:

| Event type | Event ID | Expected origin |
| --- | --- | --- |
| inference | `ai-1001-028-inference-001` | `fixture-app/inference` |
| training | `ai-1001-028-training-001` | `fixture-app/training` |
| registry | `ai-1001-028-registry-001` | `fixture-app/registry` |
| policy | `ai-1001-028-policy-001` | `fixture-app/policy` |
| runtime | `ai-1001-028-runtime-001` | `fixture-app/runtime` |

The Kubernetes audit ID is generated by the API server and is therefore intentionally not a fixed UUID. The proof records that value from the client response, finds the exact same value in the audit file, then requires that exact value at the receiver. This gives a deterministic equality check without pretending that a server-generated identifier is known before execution.

## Scope and limits

This is a local routing fixture: a small case-owned HTTP connector forwards permitted source paths to a small case-owned HTTP receiver. It proves the route's effect on these requests and records. It does not establish that a production SIEM is deployed, approved, secure, retained, complete, alerting, or usable by SOC workflows. It does not exercise an AI model, training job, model registry, policy engine, or runtime-security product; those categories are emitted as synthetic telemetry by inert one-shot fixture apps. It does not evaluate delivery completeness after onboarding; that is the distinct downstream scope of SAF-K8S-1001-029.

The route keys and event types are case-owned test semantics. They are not asserted to be a Kubernetes, Fluent Bit, SIEM, or EU AI Act standard taxonomy. No credentials or external endpoints are used. All event data, object names, namespaces, DNS names, and receiver state belong to the case.
