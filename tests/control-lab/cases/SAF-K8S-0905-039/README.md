# SAF-K8S-0905-039 adopter evidence guide

Run `python3 tests/control-lab/lab.py test SAF-K8S-0905-039 --docker-context desktop-linux` from the framework checkout.

The portable fixture demonstrates one Zot 2.1.23 repository read entitlement review: it reads the effective ACL, compares one synthetic identity and grant to a synthetic approved inventory, removes the stale grant, restarts Zot, confirms the same identity's same request is denied, and confirms an independent reader can still fetch the same manifest digest from the same PVC-backed registry. Its `120`-day age, `30`-day interval, identity labels, and owner approval are test inputs. They do not represent actual approvals, identity provenance, or an organization's schedule.

## Adoption procedure

1. **Define the review population and authoritative identity sources.** Inventory every in-scope registry product, instance, repository, and effective grant. Join registry principal IDs—not display names alone—to authoritative identity records for human users, service principals, Kubernetes workloads, groups, federated identities, and emergency accounts. Record the source that attests each principal, its accountable owner, and lifecycle state. Identify external/federated grants, inherited rules, organization-wide defaults, and API tokens that are not visible in the registry's local ACL alone.
2. **Capture ACL provenance and actual entitlement inventory.** For a dated review, preserve the registry identity/version and endpoint, repository/action rules, grant source, created/changed/expiry times, and the exported effective ACL or provider equivalent. Reconcile that state with the approved system/repository inventory and the authoritative identity/group/workload inventory. Mark missing owners, unjoined principals, stale grants, inherited access, and exceptions explicitly; do not substitute a synthetic fixture list for the production approval source.
3. **Apply the approved cadence and governance.** Document the organization-defined review interval, event-driven triggers (owner/project change, workload retirement, transfer/termination, emergency access, or registry policy change), responsible reviewer, separate repository/data owner approval, and remediation deadline. Retain the review request, source snapshot, reviewer and owner decisions, timestamps, exception rationale/expiry, and closure evidence.
4. **Remediate only the approved grant.** Use the deployed registry's supported policy API or administration workflow to remove or reduce the exact identity/repository/action grant approved for remediation. Preserve required grants and record the before/after policy diff and change authority. For clustered or cached registries, verify propagation after restart/rollout or at every serving replica.
5. **Verify effective authorization and retain evidence.** Repeat the same approved identity, repository, action, and request after the change; require the intended authorization result (for Zot, the fixture expects HTTP 403 rather than authentication failure or not-found). Independently exercise a required positive reader/action and verify the expected artifact digest or equivalent. Retain sanitized request identity, status, resource scope, policy revision, timestamps, and independent reviewer sign-off in the approved evidence store.
6. **Apply AU-6 only when audit records contribute.** Where the organization retains registry or identity audit records, document which records show grants, changes, removals, or access activity; who reviews them, at what defined frequency, how findings are reported, and how risk changes adjust review. Link this evidence to the entitlement decision. If the process uses only current ACL and approved-inventory snapshots, do not claim AU-6 from this control.

## Evidence boundary

The paired fixture proves one real Zot ACL remediation path and one preserved positive entitlement. It does not prove organization-wide inventory completeness; actual identity source, type, ownership, human authorization, or federation; periodic review operation; actual audit-record review; Harbor/MLflow/Hugging Face behavior; production propagation or deadlines; or durable production evidence retention. Those facts must be shown using the adopter's deployed systems and approved records.

## Mapping disposition

AC-2 is conditional partial support for the account-review contribution, with actual account inventory, identity provenance, frequency, and approvals supplied by the adopter. AU-6 remains conditional support only where actual attributable audit records contribute to review and reported findings; otherwise remove that relationship. The official NIST source states AC-2(j)'s organization-defined account review and AU-6's audit-record review/reporting obligations: [SP 800-53 Rev. 5, Release 5.2.0 publication](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final) and [official NIST control text](https://csrc.nist.gov/CSRC/media/Projects/risk-management/800-53%20Downloads/800-53r5/SP_800-53_v5_1-derived-OSCAL.pdf). Product behavior in the fixture is documented in the [Zot 2.1.23 authentication and authorization guide](https://zotregistry.dev/v2.1.23/articles/authn-authz/); OCI request semantics are from [Distribution Specification v1.1.1](https://github.com/opencontainers/distribution-spec/blob/v1.1.1/spec.md).
