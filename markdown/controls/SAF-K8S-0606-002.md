# SAF-K8S-0606-002 - CI/CD build environment hardening

- Domain: D06 - Supply Chain, Images, and Admission Control
- Knowledge Area: 6.6 - CI/CD and GitOps Pipeline Security
- Maturity: Practitioner
- Classification: baseline

## Statement

Run governed build jobs in distinct, job-scoped execution environments. Verify admission and workload identity restrictions, egress to required dependencies and services, and isolated writable workspace storage. Remove the environment and expire or revoke its scoped access according to the defined lifecycle. Keep release signing authority and retained diagnostics under separate controls.

## Objective

Limit a build job to authorized inputs, identity and network access, and prevent reuse of its writable state or temporary credentials.

## Rationale

Single-job placement reduces shared state only when workspace, caches, host resources and credential lifecycle are also governed. Use explicit workload and manager access roles. Remove unnecessary automatic credentials and prefer short-lived scoped identity when access is required.

## Scope

Applies to all CI/CD build infrastructure, including self-hosted Kubernetes-based runners, cloud-managed build services, and dedicated build VMs. Covers credential management for signing keys, registry credentials, cloud provider tokens, and API keys used during builds.

## Enforcement

- Primary Enforcement Point: CI runner lifecycle controls, Kubernetes Pod Security Admission or equivalent admission, workload RBAC and verified network enforcement.
- Implementation Surface: Verify a dedicated job environment, Restricted or agreed Pod standard, a distinct least-privilege job identity, explicit scoped token projection where needed, private scratch storage and enforced destination allowlists. Set runtime and cleanup bounds, check removal of Pod and isolated storage, and monitor cleanup failures. Verify the exact CI platform runner lifecycle and credential integration, including the backing environment and external credentials.
- Owner Primary: DevSecOps / Release Engineering
- Owner Supporting: Platform Engineering; Security Engineering

### NIST-800-53R5 IA-5(6)

- Framework: NIST SP 800-53 Revision 5 5.2.0
- Requirement Title: Protection of Authenticators
- Relation Type: supports
- Strength: moderate
- Applicability: conditional
- Strength Reason Code: partial-control-coverage
- Applicability Condition: Only for a selected job-scoped Kubernetes runner that uses a separately projected short-lived service-account token to access information whose classification and required protection have been documented. Verify the token scope, configured lifetime, absence of an automatic mount, least-privilege resource rules, refusal of an adjacent resource, and value-free logs. This case reads only public fixture data, does not wait for expiry, and does not cover registry, cloud, signing, or other credentials.

#### Framework Mapping Notes

For the selected disposable runner profile, the case disables the usual automatic token mount and projects a 600-second Kubernetes service-account token to a dedicated identity. Its Role permits GET on one named ConfigMap; an adjacent named ConfigMap read is denied, and receipts retain status predicates without token bytes. This is partial technical evidence for protection of that one authenticator only; it does not establish information classification, actual expiration, or protection of other build credentials.
