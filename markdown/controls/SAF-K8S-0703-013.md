# SAF-K8S-0703-013 - Topology-aware scheduling for GPU locality with blast-radius containment

- Domain: D07 - Storage, Multi-tenancy, and Resource Governance
- Knowledge Area: 7.3 - Resource Governance and Priority
- Maturity: Practitioner
- Classification: ai-specific

## Statement

Where distributed AI workloads depend on accelerator topology, use verified hardware topology data and a compatible scheduler to place the required roles within the intended locality. Where the availability design requires domain separation, distribute applicable replicas or roles across verified failure domains and test loss of a representative domain.

## Objective

Coordinate supported accelerator placement and workload availability requirements through independently verified node-local alignment, fabric locality and failure-domain distribution.

## Rationale

Kubelet Topology Manager coordinates resource hints inside a single node. Inter-node accelerator fabric placement requires authoritative hardware topology and a compatible workload scheduler. Topology spread can limit replica concentration across defined failure domains. Measure the resulting communication and recovery behavior against workload requirements.

## Scope

Applies to Kubernetes workloads whose accelerator locality or distributed availability requirements justify governed placement. Covers applicable node-local resource hint providers, authoritative accelerator and fabric topology, the workload scheduler, and the actual failure domains for training roles or serving replicas.

## Enforcement

- Primary Enforcement Point: Kubelet Topology Manager and applicable resource hint providers for node-local alignment, the compatible workload scheduler and verified topology source for fabric placement, and Pod topology spread or affinity for failure-domain distribution.
- Implementation Surface: Verify effective kubelet policy and supported CPU, memory and device hints where required. Derive fabric and clique labels from authoritative current discovery, configure the selected scheduler or integration, and check the actual assigned hardware for all distributed roles. Configure and verify the intended topology key, selector, maximum skew and unsatisfiable behavior. Validate a bounded communication workload and recovery after an approved fault where either outcome is claimed.
- Owner Primary: Platform Engineering
- Owner Supporting: ML Engineering, SRE
