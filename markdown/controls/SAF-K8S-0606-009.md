# SAF-K8S-0606-009 - SSDF v1.1 alignment for secure development practices

- Domain: D06 - Supply Chain, Images, and Admission Control
- Knowledge Area: 6.6 - CI/CD and GitOps Pipeline Security
- Maturity: Practitioner
- Classification: baseline

## Statement

Use NIST SP 800-218 SSDF v1.1 to select and document secure development practices for the approved scope. Record accountable owners, task selection or exclusion rationale, collected evidence and remediation of gaps. Identify any binding obligations from their applicable sources.

## Objective

Provide a reviewable, risk-based record of the secure development practices selected for the approved software and lifecycle scope.

## Rationale

The SSDF provides a common vocabulary and high-level recommendations for integrating secure development into a software lifecycle. Task selection, deployment evidence and any binding obligations require an applicable source and an approved organizational decision.

## Scope

The accountable owner records the software, teams, lifecycle stages and environments in scope, including Kubernetes artifacts where selected. Assess the four practice groups as applicable to that scope.

## Enforcement

- Primary Enforcement Point: Development governance and compliance review processes.
- Implementation Surface: Map selected tasks using the SSDF v1.1 practice identifiers. PO is Prepare the Organization, PS is Protect the Software, PW is Produce Well-Secured Software, and RV is Respond to Vulnerabilities. Record rationale, owners and evidence. For PO.3.2, identify the governed tools and toolchain, verify their selected security practices and retain operating and maintenance evidence.
- Owner Primary: Compliance / GRC
- Owner Supporting: DevSecOps / Release Engineering; Security Engineering

- Applicability: conditional
- Strength Reason Code: partial-control-coverage
- Applicability Condition: Only for a selected development tool where the adopter independently maintains and protects the master build data/expected digest and identifies the exact on-site tool copy. #### Framework Mapping Notes

For one selected development tool, the fixture compares the expected SHA-256 with the immutable tool bytes before execution; altered bytes fail before the tool marker is emitted, while the approved bytes execute. This is a narrow verifier example only. The developer must independently maintain and protect the mapping between current-version master build data and the on-site master copy as SA-10(5) requires.

### NIST-800-53R5 SR-3(2)

- Framework: NIST SP 800-53 Revision 5 5.2.0
- Requirement Title: Limitation of Harm
- Relation Type: supports
- Strength: moderate
- Applicability: conditional
- Strength Reason Code: partial-control-coverage
- Applicability Condition: Only when the organization documents this pre-execution tool-digest gate as one defined safeguard in its supply-chain controls and independently protects the expected digest/source identity. The fixture demonstrates refusal of inert changed public bytes; it does not establish the supply-chain risk plan, threat assessment, supplier governance, or overall supply-chain protection.

#### Framework Mapping Notes

The fixture demonstrates one technical safeguard for a development tool: changed bytes are refused before execution, while the approved fixture digest runs. This may contribute to a documented supply-chain harm-limitation control only when the expected digest comes from an independently trusted source. It is not evidence of a complete SCRM process or AI-specific supply-chain governance.

### NIST-SSDF PO.3.2

- Framework: NIST SP 800-218: Secure Software Development Framework (SSDF) Version 1.1 1.1
- Requirement Title: Follow recommended security practices to deploy, operate, and maintain tools and toolchains.
- Relation Type: supports
- Strength: moderate
- Applicability: conditional
- Strength Reason Code: partial-control-coverage
- Applicability Condition: Only for the tool-integrity verification portion of PO.3.2 when the adopter identifies a development tool and independently maintains the approved digest/source identity. The case covers digest comparison before execution and a changed-byte refusal; it does not assess tool selection, security assessment, integration, toolchain-as-code, reproducible builds, updates, monitoring, or provenance.

#### Framework Mapping Notes

The fixture verifies one tool-integrity practice by checking that immutable tool bytes match an approved expected SHA-256 before execution. It refuses changed bytes before the changed marker is emitted and executes the approved fixture. This supports only the verification slice of SSDF PO.3.2; tool selection, integration, reproducible builds, maintenance, monitoring, and provenance require separate evidence.
