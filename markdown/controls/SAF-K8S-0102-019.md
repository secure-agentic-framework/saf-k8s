# SAF-K8S-0102-019 - etcd endpoint network isolation from worker and workload traffic

- Domain: D01 - Control Plane and Cluster Hardening
- Knowledge Area: 1.2 - etcd and Cluster State Protection
- Maturity: Foundational
- Classification: baseline

## Statement

Restrict Kubernetes etcd client endpoints to the API server and other documented, approved clients required by the topology. Restrict peer endpoints to approved members and deny unapproved worker, workload and external network paths using applicable effective controls.

## Objective

Maintain intended control-plane connectivity and deny unintended access to etcd endpoint classes in the deployed network topology.

## Rationale

Network reachability, mutual TLS and authorization are distinct. The API server, required operational clients and etcd peers may need different access. Pod NetworkPolicy covers supported Pod paths while broader node, host network and provider paths require evidence at their respective boundaries.

## Scope

Applies to production Kubernetes etcd client, peer and explicitly deployed ancillary endpoints. Inventory actual addresses, ports, listeners, peer membership, approved clients, node and workload paths, and applicable provider responsibilities.

## Enforcement

- Primary Enforcement Point: Effective node, routing, provider and workload network policies together with distinct TLS and authorization at actual endpoints.
- Implementation Surface: Inventory actual listeners, peer and client access, route and network enforcement. Verify approved availability and representative denied connections for endpoint classes owned by the operator. Review host and node paths independently, and use applicable provider assurances for inaccessible managed boundaries.
- Owner Primary: Platform Engineering
- Owner Supporting: Security Engineering; Network Engineering
