# SAF-K8S-0103-005 - Pod garbage collection threshold configuration

- Domain: D01 - Control Plane and Cluster Hardening
- Knowledge Area: 1.3 - Controller-Manager, Scheduler, and Cloud Controller Security
- Maturity: Foundational
- Classification: ai-specific

## Statement

Production Kubernetes clusters must configure or verify a positive controller-manager terminated Pod garbage collection threshold (--terminated-pod-gc-threshold) appropriate to the cluster's batch workload and diagnostic retention needs. Verify that PodGC removes excess Succeeded and Failed Pod objects when their cluster-wide count exceeds the effective threshold. If a workload requires a maximum retention age, define and verify it through a separate lifecycle policy.

## Objective

Bound the accumulation of terminated Pod objects and the associated metadata retained in the API server.

## Rationale

Terminated Pod objects can retain environment variable references, volume mounts, image references, and exit status. PodGC uses a cluster-wide count instead of a per-namespace count or a deadline. The Kubernetes v1.36 default is 12500; a nonpositive threshold disables count-based terminated Pod collection. Batch-heavy clusters can choose a smaller positive threshold while retaining enough diagnostic history.

## Scope

Applies to all production Kubernetes clusters. Particularly relevant for clusters running batch AI workloads (distributed training, pipeline jobs) that create large numbers of short-lived pods. For managed Kubernetes services, verify whether the provider exposes this setting or applies a default threshold.

## Enforcement

- Primary Enforcement Point: Controller-Manager Configuration
- Implementation Surface: Effective controller-manager flag or provider documentation, and cluster-wide observation of terminated Pod counts and collection behavior.
- Owner Primary: Platform Engineering
- Owner Supporting: Security Engineering; AI/ML Engineering
