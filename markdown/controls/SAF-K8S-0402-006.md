# SAF-K8S-0402-006 - Cloud workload identity federation for AI services

- Domain: D04 - Identity, Access, and Secrets Management
- Knowledge Area: 4.2 - Service Accounts and Workload Identity
- Maturity: Practitioner
- Classification: ai-specific

## Statement

For governed workloads accessing cloud services, require the approved provider-specific workload identity path and effective least-privilege access. Prevent unauthorized static cloud-key use and verify each identity and credential transition under the actual provider and platform configuration.

## Objective

Verify the expected workload principal, effective scoped cloud authorization, and absence of unapproved credential fallback for governed operations.

## Rationale

Provider integrations differ in identity binding, trust, credential exchange and runtime delivery. A Kubernetes token is distinct from a cloud credential obtained using it. Federation does not prevent an application from receiving or loading a static key through another path.

## Scope

Applies to governed Kubernetes workloads accessing external cloud services with AWS, Google Cloud, Microsoft Entra, or other approved providers. Record the exact provider, credential source, authorized service and required isolation.

## Enforcement

- Primary Enforcement Point: Provider-specific workload trust and effective authorization with independently verified Kubernetes admission, token projection and static credential boundaries.
- Implementation Surface: Distinguish EKS IRSA annotations and OIDC trust from EKS Pod Identity associations and agent prerequisites. Verify the selected GKE direct principal or linked-account mode, and check relevant AKS workload labels, issuer and identity binding. Test actual issuer and subject restrictions, granted cloud actions, credential delivery and renewal, failed and fallback paths, and applicable revocation.
- Owner Primary: Platform Engineering
- Owner Supporting: Cloud Platform Engineering; ML Engineering; Security Engineering
