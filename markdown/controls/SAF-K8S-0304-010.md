# SAF-K8S-0304-010 - Pod resource requests and limits specification

- Domain: D03 - Workload and Pod Security
- Knowledge Area: 3.4 - Secure Defaults and Resource Constraints
- Maturity: Foundational
- Classification: baseline

## Statement

Require explicit CPU, memory and local ephemeral-storage requests and limits for regular and init containers in in-scope workload Pods.

## Objective

Supply measured resource inputs for scheduling and applicable runtime enforcement.

## Rationale

Requests inform scheduling. Linux CPU limits constrain execution through throttling and memory limits can trigger OOM termination. Local ephemeral-storage limits depend on kubelet accounting and can result in eviction. Individual declarations are one input alongside aggregate quota, node capacity and usage monitoring.

## Scope

Applies to regular and init containers in workload Pods. Where accelerators are required, declare the allocation mechanism appropriate to the platform, such as a vendor extended resource. Address aggregate accelerator quotas separately.

## Enforcement

- Primary Enforcement Point: Validate authored rendered Pod templates before API defaulting. Use admission to enforce the effective resource fields.
- Implementation Surface: Validate the applicable resources.requests and resources.limits entries in regular and init containers in rendered templates and admitted Pods. Verify defaulting, scheduling and runtime behavior for approved budgets. For device-plugin resources, confirm the expected resource key and actual allocation. Preserve the scope of local storage accounting or eviction.
- Owner Primary: Platform Engineering
- Owner Supporting: Application Development teams; AI/ML Platform team (for GPU resource requests)
