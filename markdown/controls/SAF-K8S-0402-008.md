# SAF-K8S-0402-008 - Distinct identity assignment for AI workload types

- Domain: D04 - Identity, Access, and Secrets Management
- Knowledge Area: 4.2 - Service Accounts and Workload Identity
- Maturity: Practitioner
- Classification: ai-specific

## Statement

Training jobs, inference servers, and ML pipeline components must each be assigned distinct Kubernetes service accounts with role-appropriate permissions, and must not share service accounts across workload types with differing access requirements.

## Objective

Enforce identity segmentation between AI workload types so that a compromised inference server cannot access training data storage, and a compromised pipeline component cannot modify serving endpoints.

## Rationale

AI workloads have fundamentally different access needs: training jobs require read access to training data and write access to model storage; inference servers require read access to model artifacts and may need access to feature stores; pipeline orchestrators require permissions to create and manage jobs. Sharing a single service account across these workload types violates least privilege and means that compromising any one component grants access to resources needed by all others.

## Scope

Applies to all clusters running AI/ML workloads. Covers Kubeflow pipelines, KServe inference services, training operators, notebook servers, and any custom ML components. Each distinct workload type within a namespace must have its own service account.

## Enforcement

- Primary Enforcement Point: Namespace-scoped service account definitions per AI workload type, with admission policies that validate pod service account assignments match the expected workload type based on labels or annotations.
- Implementation Surface: Per-workload-type Kubernetes ServiceAccount definitions (sa-training, sa-inference, sa-pipeline, sa-notebook), namespace-scoped RBAC Roles with differentiated permissions per AI workload type, admission policies (OPA Gatekeeper, Kyverno) validating pod-to-service-account mappings based on workload labels or annotations, KServe InferenceService, Kubeflow Training Operator, and pipeline orchestrator service account assignment configurations.
- Owner Primary: ML Engineering
- Owner Supporting: Platform Engineering; Security Engineering
