# SAF-K8S-0102-006 - etcd encryption key rotation scheduling and verification

- Domain: D01 - Control Plane and Cluster Hardening
- Knowledge Area: 1.2 - etcd and Cluster State Protection
- Maturity: Foundational
- Classification: baseline

## Statement

Define and exercise a key rotation schedule for applicable Kubernetes API data encryption. Verify active write-key selection, readability and migration of data protected by prior keys, and retirement only after the applicable migration and recovery checks succeed. Verify remote KMS key rotation at the provider boundary.

## Objective

Maintain current approved encryption keys while preserving protected data availability and proving completion of any required storage migration.

## Rationale

Changing provider or key selection for new writes and rewriting previously stored objects are distinct operations. Kubernetes local provider rotation differs from remote key-encryption-key lifecycle and managed control-plane evidence. Use version-specific and applicable provider guidance.

## Scope

Applies to governed Kubernetes API server encryption-at-rest configurations and selected resource coverage. Record local keys, remote key-encryption keys, supported configuration reload, migration, provider responsibilities, version, cadence, exception and rollback requirements.

## Enforcement

- Primary Enforcement Point: Effective API server encryption configuration and observed protected object writes and reads, with KMS policy and key lifecycle evidence where provider-managed.
- Implementation Surface: Record the approved interval and rotation trigger, active key selection, prior-key read window, migration progress, retirement criteria and rollback. For remote KMS use approved provider evidence and verify active key identifiers and integration health without retaining key material.
