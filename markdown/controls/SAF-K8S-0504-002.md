# SAF-K8S-0504-002 - Service mesh mTLS and authorization policies

- Domain: D05 - Network Security and Communication
- Knowledge Area: 5.4 - Zero Trust Architecture and Service Mesh
- Maturity: Practitioner
- Classification: baseline

## Statement

Deploy a service mesh that automatically authenticates both workload peers and encrypts their service traffic, restricts communication by workload identity, and collects request-level metrics and distributed traces. Where authentication is out of band, separately enable and verify encryption for every covered traffic path.

## Objective

Establish transparent, identity-based encryption and authorization for all service communication with full traffic observability.

## Rationale

A service mesh can centralize identity issuance, transport protection, authorization, and observability. Confirm the selected implementation and configuration protect each intended application path, including same-node communication and workloads excluded from automatic enrollment.

## Scope

Applies to all production Kubernetes clusters with multi-service architectures. The service mesh must cover all application workloads. System namespaces may be excluded if compensating controls exist. Performance overhead of sidecar proxies must be evaluated and documented.

## Enforcement

- Primary Enforcement Point: Service mesh control plane configuration (Istio PeerAuthentication and AuthorizationPolicy; Linkerd Server, AuthorizationPolicy and MeshTLSAuthentication), sidecar injection policies, and mesh-level telemetry pipelines.
- Implementation Surface: Service mesh control plane (Istio, Linkerd, Cilium service mesh), Istio PeerAuthentication resources (STRICT mTLS mode), Istio AuthorizationPolicy resources restricting inter-service communication by service account principal, Linkerd Server and HTTPRoute with AuthorizationPolicy, release-appropriate Cilium workload authentication, L7 CiliumNetworkPolicy, and separately configured data-path encryption such as WireGuard or IPsec. Cilium v1.20 deprecates beta SPIRE-backed out-of-band mutual authentication, and the v1.21 development upgrade guide documents its removal. Verify same-node protection separately when using WireGuard. Verify sidecar injection, namespace enrollment, request metrics, distributed traces, and compensating controls for mesh exclusions.
- Owner Primary: Platform Engineering
- Owner Supporting: Network Engineering; Security Engineering; Application Development

- Relation Type: supports
- Strength: moderate

- Strength Reason Code: partial-control-coverage

#### Framework Mapping Notes

The local case observes distinct Istio workload service-account principals at the destination proxy and enforces an identity-scoped request policy. The separate Cilium runtime case observes SPIRE workload authentication for its exact fixture pair. This supports service identification and authentication for these tested paths only; it does not establish production identity governance, all-service coverage, or Linkerd behavior.
