# SAF-K8S-0603-005 - FIPS 140 cryptographic module validation

- Domain: D06 - Supply Chain, Images, and Admission Control
- Knowledge Area: 6.3 - Attestation, Provenance, and Cryptographic Assurance
- Maturity: Practitioner
- Classification: baseline

## Statement

Where an applicable requirement calls for FIPS 140 validated cryptography, use the applicable CMVP-validated module and version for each in-scope signing and verification operation. Verify the deployed operational environment, approved mode and permitted services against the certificate and security policy. Assess key custody within its own applicable boundary.

## Objective

Establish evidence that the deployed signer and verifier use the applicable validated cryptographic module under the conditions in its security policy.

## Rationale

CMVP evaluates a defined cryptographic module, version and configuration. Its certificate and security policy define approved services, supported operating conditions and caveats. Evaluate the integrating application, runtime provider selection and key custody separately.

## Scope

Applies to all signing and verification operations for container images, attestations, SBOMs, model artifacts, and Helm charts. Includes HSM-backed signing, software-based signing libraries, and verification libraries in admission controllers. Organizations not subject to FIPS requirements must document their cryptographic module assurance strategy.

## Enforcement

- Primary Enforcement Point: Signing infrastructure provisioning and cryptographic library selection during build system configuration.
- Implementation Surface: Record the governing requirement, active or otherwise applicable CMVP certificate, exact module build and version, operational environment, approved services and parameters, and observed runtime provider selection. Match each signing, verification or cloud key-custody service to its own module evidence. Verify applicable mode and control settings at provisioning and during operation.
- Owner Primary: Security Engineering
- Owner Supporting: Platform Engineering; Compliance / GRC

### NIST-800-53R5 SC-13

- Framework: NIST SP 800-53 Revision 5 5.2.0
- Requirement Title: Cryptographic Protection
- Relation Type: supports
- Strength: moderate
- Applicability: conditional
- Strength Reason Code: partial-control-coverage
- Applicability Condition: Use this relationship only for the specifically assessed signing or verification operation after separately establishing that its deployed module build, approved mode, service, and operational environment meet an applicable CMVP certificate and security policy. The fixture does not establish those deployment facts or the organization-wide cryptographic-use inventory.

#### Framework Mapping Notes

The paired fixture selects the OpenSSL FIPS provider with an explicit fips=yes property query, verifies its generated integrity configuration, rejects a 1024-bit RSA request, and performs RSA-2048/SHA-256 signing and verification on one synthetic artifact. This is a bounded provider-operation comparison; it does not by itself prove the locally rebuilt module is the validated CMVP module or that an adopter has determined and implemented all required cryptographic uses.

### NIST-800-53R5 SI-7(6)

- Framework: NIST SP 800-53 Revision 5 5.2.0
- Requirement Title: Cryptographic Protection
- Relation Type: supports
- Strength: moderate
- Applicability: conditional
- Strength Reason Code: partial-control-coverage
- Applicability Condition: Apply only to an in-scope software or information integrity check using the same verified signature path, and separately establish applicable CMVP build, mode, service, and environment evidence where required. This fixture does not establish deployed key custody, verification coverage, or response to integrity violations.

#### Framework Mapping Notes

The paired fixture signs a harmless artifact and verifies the signature against both the original and a changed artifact; verification of the changed artifact fails. This demonstrates one cryptographic integrity mechanism. It does not establish an adopter-wide integrity program, deployed verifier path, key protection, or action after detection.
