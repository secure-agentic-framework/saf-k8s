# SAF-K8S-0901-002 - Parameter server and all-reduce security

- Domain: D09 - AI Workload Security: Training, Serving, and Pipelines
- Knowledge Area: 9.1 - Distributed Training Workload Security
- Maturity: Advanced
- Classification: ai-specific

## Statement

Operators using parameter servers or collective aggregation must define authorized participants and update-acceptance criteria for each deployed aggregation path. Enforce the applicable identity, membership and input-integrity checks before contributions affect an aggregate. Where the documented threat model includes malicious participants or Byzantine faults, select and test resilience controls compatible with the training architecture and aggregation protocol.

## Objective

Limit participation and accepted updates to the approved aggregation scope. Define and verify the training system's response to anomalous or malicious contributions where applicable. Base any claimed poisoning or Byzantine resilience on evidence for the compatible aggregation and model-quality controls.

## Rationale

A parameter server can receive individual updates at a central interface where identity, assignment and input-eligibility checks occur before inclusion. A collective such as all-reduce combines participant tensors and distributes the reduction result. Document the controls provided by the process-group and training stack, and verify authentication, update checks, monitoring and robustness where relevant. Enrollment and numeric validity address membership and format. Resistance to malicious contributions requires evidence for the selected training procedure.

## Scope

Applies to distributed training workloads using parameter servers or collective aggregation, including synchronous and asynchronous configurations. Identify the actual aggregation interfaces, participant membership and safeguards for each in-scope topology. Include the separately evidenced resilience mechanisms where required by the documented threats.

## Enforcement

- Primary Enforcement Point: The training operator and workload identity or process-group membership configuration, together with the parameter-server aggregation interface or the architecture-specific collective participation and reduction boundary.
- Implementation Surface: Document the topology, aggregation protocol, trust assumptions, and authorized participant set. Enforce identity and membership at the actual admission boundary. Validate update schema and model-specific eligibility before an update can affect an aggregate wherever the architecture exposes that boundary. For collectives, document where such checks occur and what individual contributions remain observable. Record bounded acceptance, rejection, and anomaly decisions. If malicious-participant or Byzantine resilience is required, select an aggregation or protocol compatible with the deployed architecture and any secure-aggregation/privacy controls, then test its stated assumptions, fault tolerance, failure behavior, and model-quality effects. Verify transport protection and monitoring separately for each required path.
