# SAF-K8S-0903-003 - Inference-time resource controls

- Domain: D09 - AI Workload Security: Training, Serving, and Pipelines
- Knowledge Area: 9.3 - Inference Resilience, Adversarial Defense, and Resource Controls
- Maturity: Practitioner
- Classification: ai-specific

## Statement

Inference workloads must enforce computational complexity bounds per request, input size restrictions, multi-level timeouts (request, session, batch), GPU memory ceilings per inference pod, and overload handling mechanisms including graceful degradation and circuit breakers to prevent Economic Denial of Sustainability (EDoS) attacks.

## Objective

Bound the resource consumption of individual inference requests and overall inference workloads to prevent resource exhaustion, cost overruns, and denial-of-service through computational abuse.

## Rationale

Without per-request computational bounds, inputs can consume excessive inference time and cluster resources. GPU memory ceilings require a device-specific mechanism: Kubernetes GPU extended-resource requests and quotas account for schedulable device quantities but do not by themselves impose a per-Pod GPU-memory ceiling. Where that ceiling is required, use and verify a supported hardware/runtime partition or memory-control mechanism, such as an applicable MIG or vGPU profile. Without circuit breakers and graceful degradation, overload conditions can cascade into service outages. EDoS risk also requires controls on cloud capacity and cost.

## Scope

Applies to all inference pods running on Kubernetes with GPU or accelerator resources. Covers per-request limits, per-pod resource ceilings, and infrastructure-level overload protection. Includes cloud-hosted inference services where EDoS risk applies. Excludes training workloads, which have separate resource controls under KA 9.1.

## Enforcement

- Primary Enforcement Point: Inference server configuration (timeout and input size settings), Kubernetes CPU and host-memory resource limits, GPU device-plugin resource requests and quotas for schedulable device quantities, supported device-specific GPU-memory partition or limit configuration where required, and service-mesh or server circuit-breaker configuration.
- Implementation Surface: Inference server configuration (per-request timeouts, maximum input size, batch size, output tokens, beam width, and session limits); Kubernetes CPU and host-memory resource limits; GPU device-plugin extended-resource requests and quotas for device counts; and, only on supported hardware/runtime configurations, an explicit MIG/vGPU partition or memory-control policy with the effective profile and per-Pod allocation verified. Device-count requests or quotas alone are not GPU-memory ceilings. Include service-mesh or server circuit-breaker configuration (such as a supported Istio or Envoy mechanism), graceful degradation behavior, and applicable per-request cost controls.
- Owner Primary: ML Platform Engineering
- Owner Supporting: Platform Engineering; Security Engineering; FinOps
