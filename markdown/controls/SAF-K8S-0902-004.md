# SAF-K8S-0902-004 - Multi-model serving isolation and encryption

- Domain: D09 - AI Workload Security: Training, Serving, and Pipelines
- Knowledge Area: 9.2 - Inference Server and Model Serving Security
- Maturity: Practitioner
- Classification: ai-specific

## Statement

Multi-model serving deployments must isolate per-model state and shared memory, account for each model's use of shared resources, and enforce per-model resource bounds where models or tenants share a serving runtime or accelerator. If the shared deployment cannot verify the required isolation and accounting, place the models in separately enforced resource and trust boundaries. Protect all external and internal inference traffic with TLS across every network hop and require mutual TLS for internal model-to-model or service-to-service inference paths. Verify transport coverage and peer identity. Single-model deployments remain subject to inference-transport protections.

## Objective

Protect model and tenant data from unintended access through shared serving resources, reduce resource-exhaustion interference, and protect inference information in transit on applicable paths.

## Rationale

Multi-model serving may place models in a shared process, runtime, Pod, or accelerator, but the isolation boundary depends on the chosen architecture. Shared-memory separation, process isolation, resource bounds, and accelerator partitioning are distinct mechanisms and must be selected and verified for the deployment. A scheduler or model-instance limit alone does not establish GPU-memory isolation. TLS protects inference data in transit only on the paths where it is configured; mutual TLS additionally authenticates peers when both ends validate credentials.

## Scope

Applies to Kubernetes inference deployments that host multiple models or tenants in a shared serving process, Pod, node, or accelerator, and to inference ingress and service-to-service paths. Select isolation and resource controls that match the runtime and hardware. For example, KServe ModelMesh Serving marks compatible runtimes as multi-model and coordinates model load/unload capacity; this is not by itself a per-model process or GPU-memory isolation guarantee. Triton can load and schedule multiple models in one server process; its rate limiter controls execution scheduling and should not be represented as model-specific GPU-memory isolation. Single-model deployments remain in scope for applicable inference-transport protections.

## Enforcement

- Primary Enforcement Point: Serving-runtime and Kubernetes workload boundaries, supported accelerator partitioning and resource-allocation controls, and validated TLS at ingress and mutual TLS for internal inference hops.
- Implementation Surface: Choose controls supported by the deployed runtime and hardware: separate processes or Pods and scoped shared-memory mounts where those are the intended boundaries; Kubernetes requests/limits for supported CPU and memory resources; supported GPU partitioning such as NVIDIA MIG on compatible hardware when hardware-enforced accelerator partitions are required; and runtime scheduling/resource controls only for the behaviors they document. NVIDIA GPU time-slicing shares a GPU without isolating memory/fault domains, so do not describe it as GPU-memory isolation. Configure TLS at ingress and mutual TLS on internal inference paths, then assess coverage and peer verification for each path. Bind resource measurements to the covered model and its assigned runtime or device boundary. Monitor GPU metrics at the granularity the exporter or runtime exposes; do not call per-GPU metrics per-model accounting unless attribution is available and validated.
