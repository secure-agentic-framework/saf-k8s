# SAF-K8S-0905-040 - Model registry audit event generation and centralized forwarding

- Domain: D09 - AI Workload Security: Training, Serving, and Pipelines
- Knowledge Area: 9.5 - AI Supply Chain and Model Lifecycle
- Maturity: Practitioner
- Classification: ai-specific

## Statement

Model registries must generate audit logs for model publish, pull, tag, permission, deletion, and administrative operations and must forward those events to centralized monitoring or SIEM platforms with verified delivery and retention.

## Objective

Create reliable telemetry coverage for model-registry abuse by ensuring registry operations are recorded and forwarded into centralized monitoring.

## Rationale

Registry compromises often manifest first as unusual publish, pull, deletion, or permission-change activity. Without complete event generation and forwarding, malicious model substitution, unauthorized access, and registry tampering can occur without durable telemetry or centralized visibility.

## Scope

Applies to all model registry deployments on Kubernetes, including Harbor, MLflow Model Registry, and on-premises Hugging Face Hub instances. Covers registry audit event generation and forwarding into centralized monitoring. Excludes alert triage and operational review procedures.

## Enforcement

- Primary Enforcement Point: Registry audit log configuration and forwarding pipeline into centralized monitoring or SIEM.
- Implementation Surface: Registry audit log enablement, event export or webhook forwarding, log ingestion verification, and delivery checks for sensitive registry operations.
- Owner Primary: ML Platform Engineering
- Owner Supporting: Security Engineering; Platform Engineering

## Related Crosswalks

### NIST-800-53R5 AU-12

- Framework: NIST SP 800-53 Revision 5 5.2.0
- Requirement Title: Audit Record Generation
- Relation Type: supports
- Strength: moderate
- Applicability: conditional
- Strength Reason Code: partial-control-coverage
- Applicability Condition: Only for adopter-defined registry event types and components for which the deployed registry demonstrably generates and forwards the selected audit record content; the reference fixture covers Zot v2.1.23 manifest publish, pull, retag, and digest deletion only.

#### Framework Mapping Notes

The fixture observes the selected Zot v2.1.23 registry actions in native audit and HTTP access records and forwards the exact matching records to a separate receiver. It does not establish administrative or permission-change event coverage, all-registry applicability, or required retention; those event sources and requirements must be verified for the adopter's defined AU-2 event set.

### NIST-800-53R5 AU-12(1)

- Framework: NIST SP 800-53 Revision 5 5.2.0
- Requirement Title: System-wide and Time-correlated Audit Trail
- Relation Type: supports
- Strength: moderate
- Applicability: conditional
- Strength Reason Code: partial-control-coverage
- Applicability Condition: Only where the adopter defines the relevant system components and time-correlation tolerance, verifies clock behavior for those components, and demonstrates their records are compiled into the central trail; the fixture covers two log streams from one Zot instance and preserves their original timestamps during forwarding.

#### Framework Mapping Notes

The fixture confirms equality of source timestamps in the selected Zot audit/access records and the received corpus, but does not test a multi-component clock-tolerance bound or establish system-wide coverage. The organization-defined component set and time-correlation tolerance remain adopter requirements.
