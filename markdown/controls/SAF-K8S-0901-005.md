# SAF-K8S-0901-005 - Federated learning security on Kubernetes

- Domain: D09 - AI Workload Security: Training, Serving, and Pipelines
- Knowledge Area: 9.1 - Distributed Training Workload Security
- Maturity: Advanced
- Classification: ai-specific

## Statement

Federated learning deployments on Kubernetes must implement secure aggregation protocols, differential privacy for gradient updates, Byzantine-resilient aggregation, authenticated participant enrollment, and namespace-level isolation of federated training participants to prevent gradient leakage and model inversion attacks.

## Objective

Protect the confidentiality of participant data and the integrity of the global model in federated learning by securing the aggregation process and isolating participants from one another.

## Rationale

Federated learning shares gradient updates rather than raw data, but gradients can still leak sensitive training data through gradient inversion attacks. Without secure aggregation, the central server can observe individual participant contributions. Without Byzantine-resilient aggregation, a malicious participant can poison the global model. Without participant isolation, compromised participants can attack others through shared infrastructure.

## Scope

Applies to all federated learning workloads orchestrated on Kubernetes, including cross-silo and cross-device configurations. Covers the aggregation server, participant worker pods, and inter-participant communication channels. Does not apply to centralized training where all data is co-located.

## Enforcement

- Primary Enforcement Point: Federated learning operator configuration, aggregation server deployment manifests, participant namespace isolation policies, and network policies restricting cross-participant communication.
- Implementation Surface: Federated learning framework deployments (Flower, FATE/KubeFATE, NVIDIA FLARE, TensorFlow Federated), secure aggregation protocol configuration (SecAgg), differential privacy parameters (epsilon, delta, DP-SGD), Byzantine-resilient aggregation algorithms (Krum, coordinate-wise median), SPIFFE/SPIRE identity federation for participant authentication, Kubernetes namespace isolation per participant, NetworkPolicy restricting cross-participant communication, FL enrollment registry, privacy budget tracking, and transport protection for aggregation and update channels appropriate to the deployment boundary. Use and verify cross-cluster mutual TLS where participant or aggregation components communicate across Kubernetes clusters.
- Owner Primary: ML Platform Engineering
- Owner Supporting: Security Engineering; Privacy Engineering
