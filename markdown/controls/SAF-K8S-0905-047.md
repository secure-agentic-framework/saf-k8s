# SAF-K8S-0905-047 - Training pipeline attestation generation for ML artifacts

- Domain: D09 - AI Workload Security: Training, Serving, and Pipelines
- Knowledge Area: 9.5 - AI Supply Chain and Model Lifecycle
- Maturity: Advanced
- Classification: ai-specific

## Statement

In-toto or equivalent attestations must be generated for the training and build pipeline steps that produced internal ML artifacts so the provenance of those artifacts can be independently evaluated.

## Objective

Establish verifiable provenance for internally produced ML artifacts by generating attestations that record how the artifacts were built.

## Rationale

Cryptographic signatures prove artifact integrity, but not how the artifact was produced. Training pipeline attestations provide verifiable build-step provenance, inputs, and workflow evidence that downstream trust decisions depend on.

## Scope

Applies to models, training input manifests, intermediate pipeline artifacts, final outputs, and related provenance records generated by internal ML training and packaging pipelines. Covers attestation generation for training and build steps, but not deploy-time verification or registry retention policies.

## Enforcement

- Primary Enforcement Point: Training attestation generation workflow.
- Implementation Surface: In-toto attestation generation for training pipeline steps, provenance predicate capture, attestation subjects for models and related artifacts, and attestation storage alongside OCI model artifacts.
- Owner Primary: ML Platform Engineering
- Owner Supporting: Security Engineering; DevOps Engineering

#### Framework Mapping Notes

NIST SP 800-53 Rev. 5 SR-4 requires documenting, monitoring, and maintaining valid provenance for organization-defined systems, system components, and associated data. This control makes a scoped technical contribution by generating signed in-toto/SLSA provenance for training and packaging steps and attaching the envelopes to the synthetic package in an OCI registry. The paired disposable-cluster receipts verify the fixture statements, expected material/subject digests, and OCI digest round-trip. They do not establish complete source/process/personnel identity, full lifecycle change monitoring, production workflow coverage, or provenance custody/transfer. Adoption must define the covered elements, bind statements to authenticated builder identities, and maintain and monitor the resulting provenance records.

### NIST-SSDF PS.2.1

- Framework: NIST SP 800-218: Secure Software Development Framework (SSDF) Version 1.1 1.1
- Requirement Title: Make software integrity verification information available to software acquirers.
- Relation Type: supports
- Strength: moderate
- Applicability: conditional
- Strength Reason Code: partial-control-coverage
- Applicability Condition: Only when an organization distributes the covered ML artifact as software to acquirers and makes the integrity-verification information and trust instructions available to them. The reference proves fixture-local OCI attachment/retrieval, not acquirer availability or a production trust channel.

#### Framework Mapping Notes

NIST SP 800-218 SSDF PS.2.1 calls for making software integrity-verification information available to software acquirers. This fixture publishes its synthetic in-toto/DSSE provenance as OCI attachments and retrieves those exact bytes by digest. It does not establish that covered ML artifacts are software releases made available to acquirers, that acquirers can retrieve verification information, or that they have an independent approved trust anchor and instructions. Apply only where the organization distributes these artifacts as software; adoption must provide an acquirer-usable verification method, trusted signer information, key lifecycle/revocation guidance, and authenticated artifact/attestation access.
