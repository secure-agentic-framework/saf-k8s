# SAF-K8S-0902-006 - LLM serving configuration security

- Domain: D09 - AI Workload Security: Training, Serving, and Pipelines
- Knowledge Area: 9.2 - Inference Server and Model Serving Security
- Maturity: Practitioner
- Classification: ai-specific

## Statement

LLM inference servers must enforce secure configuration of LLM-specific serving subsystems including KV cache memory isolation between concurrent requests, continuous batching queue depth and priority controls, and prefix caching tenant isolation to prevent cross-request information leakage and resource exhaustion through serving-layer misconfigurations.

## Objective

Prevent cross-request data leakage and resource abuse through secure configuration of LLM-specific serving subsystems (KV cache, continuous batching, prefix caching) that have no equivalent in traditional inference servers.

## Rationale

LLM serving engines retain attention state and may share prefix-cache entries within a process. Protect request and tenant boundaries by choosing a supported cache lifecycle and isolation policy. Shared-process prefix reuse can expose information through timing. Tenant-scoped cache keys can reduce unauthorized reuse, while process or instance isolation can provide a separate boundary where required. Independently bound active sequences, pending work and per-request generation so a workload cannot consume capacity intended for other requests.

## Scope

Applies to all LLM-specific inference servers deployed on Kubernetes, including vLLM, TGI, and Triton with LLM backends. Covers KV cache configuration, continuous batching parameters, and prefix caching settings. Does not apply to non-generative model serving (image classification, embedding models) where these subsystems are absent.

## Enforcement

- Primary Enforcement Point: Version-specific serving-engine and authenticated ingress or admission settings, cache ownership and memory lifecycle controls, and verified process or hardware boundaries where required.
- Implementation Surface: Select version-supported context length, accelerator memory budget, active-sequence limits, request deadlines, and pending-work limits. For vLLM, max_num_seqs sizes scheduler or runner concurrency; separately verify admission and pending capacity for the chosen version and topology. Verify release and reuse of KV cache state and any required physical memory clearing using supported runtime or hardware behavior. Bind prefix-cache reuse to authenticated tenant configuration where supported, or use separate serving instances when the trust boundary requires them. Measure actual cache, queue, priority and resource behavior for the adopted engine and policies.

- Owner Supporting: Security Engineering; Platform Engineering
