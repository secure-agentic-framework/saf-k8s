# SAF-K8S-0803-003 - RDMA memory region and queue pair isolation

- Domain: D08 - GPU, Accelerator, and Confidential Computing
- Knowledge Area: 8.3 - High-Performance Interconnect Security
- Maturity: Advanced
- Classification: ai-specific

## Statement

Verify RDMA memory and queue access against approved workload protection domains, scoped access permissions and lifecycle policy. Validate provider and device assignment and peer DMA separately from Kubernetes admission and resource accounting.

## Objective

Constrain approved RDMA registrations and queue ownership to the intended workload trust boundary.

## Rationale

RDMA memory registration and queue configuration occur in the application, provider verbs and hardware layers. Kubernetes admission and Linux RDMA cgroups can govern declarations or resource counts. These observations do not establish protection domain ownership or effective access permissions.

## Scope

Applies to governed RDMA workload paths, including host and accelerator memory, protection domains, queue ownership and lifecycle, supported devices, network and provider-only controls.

## Enforcement

- Primary Enforcement Point: Effective workload and provider RDMA access policy, protected lifecycle evidence and independent platform assignment.
- Implementation Surface: Inventory applicable workload and device paths and the reviewed trust boundary. Verify actual memory permissions, protection-domain and queue ownership, registration lifecycle and read-only provider evidence. Restrict declared device access and assess fabric and DMA controls separately. Record missing or stale measurements.
- Owner Primary: ML Platform Engineering
- Owner Supporting: Network Engineering; GPU Infrastructure Engineering; Security Engineering
